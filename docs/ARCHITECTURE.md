# 架构说明

当前架构为 React/Vite 工作台、FastAPI 服务、SQLite 和本地媒体目录。常规产品默认 `Settings.progressive_planning_enabled=True`：策略及方向审核通过后等待用户选择，选择后执行 `ad_script`（内容稿）、`storyboard`（分镜协调）、`plan_review`（最终方案综合审核）三个核心请求。分镜协调未固定的草稿内容，程序随后确定最终时间，再交独立审核。确定性的服务端流程负责校验、确认、恢复和合成；模型不能任意执行系统命令或无限重试付费生成。

## 模块职责

| 模块 | 职责 |
|---|---|
| `frontend/` | 项目导航、统一对话输入、澄清与图片检查卡、方案编辑、画布、播放和下载 |
| `app/main.py` | HTTP、上传、本地连接设置、公开数据序列化、SSE 和单 worker 调度 |
| `app/schemas.py` | 项目、问题、回答、计划和确认请求的结构校验 |
| `app/planning.py` | 策略/分镜契约、内容组与独立旁白时段安排、商家证据来源和旧审稿兼容 |
| `app/ad_script.py` | 广告内容合同、六项内容检查结构、引用及预算约束，旧 ScriptReview 兼容 |
| `app/progressive_planning.py` | 内容与分镜联合稿、coverage 编译、最终时轴、最多两轮局部修正及范围保护 |
| `app/plan_review.py` | 最终方案综合审核契约、完整检查与方案内容哈希绑定 |
| `app/production.py` | 已选商品/角色/声音约定、局部出镜与同一人物声音延续权限、角色参考图需求；历史缺省保持原语义 |
| `app/runtime_skills.py`、`app/skills/registry.json`、`app/skills/ads-video-*/` | 按阶段读取正式 Skill、编译媒体模板、记录实际版本与哈希；pending 能力不冒充已执行 |
| `app/av_review.py` | 综合审核复用的 AV 合同，核对全部实际镜头/台词时段与 pacing；新声音延续逐相交镜头核对可见性；旧 alignment_review 兼容 |
| `app/strategy.py`、`app/strategy_rules.json` | 本地创意规则、商品事实与方向结构、规则前提及来源引用校验 |
| `app/db.py` | SQLite 中的项目修订、会话、任务、确认节点、回执与素材索引 |
| `app/providers/gateway.py` | 按配置选择文本策划供应商、土豆网关图片/视频接口、受控下载与旧 TTS 兼容 |
| `app/planner_transport.py` | 固定供应商地址、对应凭据及请求参数转换；当前本地策划使用土豆 API 的 gpt-6-sol，保留旧 DeepSeek 配置兼容 |
| `app/evidence_references.py` | 新策略请求中商家来源使用短编号，精确映射回真实ID；不改引文或按相似度猜测来源，历史存储保持原ID |
| `app/pipeline.py` | 冻结任务输入、准备场景、暂停确认、生成、恢复、取消和合成发布 |
| `app/media.py` | 媒体测量、裁切、规格归一化、原音保留与 FFmpeg 合成 |

供应商模型和可用能力由当前适配器约束，不是假设所有服务均遵循相同视频 API。更换模型需要重新核验参考图、时长、任务返回、音轨和下载协议。

## 对话与确认

```text
需求、商品图片、已答问题、当前方案
                  ↓
             strategy 理解与路由
          ↙       ↓       ↘
       直接回复   澄清题   3 个候选方向
                  ↓        ↓
              汇总回答  direction_review
                           ↓
                       用户选择方向
                           ↓
          storyboard 文案与分镜联合起稿（开关开启）
          或 ad_script 内容稿 → storyboard 分镜协调
                           ↓
                    程序排定最终时间
                           ↓
                  plan_review 综合审核
                 ↙                     ↘
       最多两轮 plan_refinement         审核通过
       重排时间后独立全审               ↓
                                  用户确认方案
                                       ↓
                             复用原图、生成场景与角色图
                                       ↓
                                  用户检查图片
                                ↙            ↘
                           提交修改         确认继续
                              ↓                ↓
                            回策划         视频生成与合成
```

模型可以在入口回复里用 `next_step` 或 `next_steps` 指定下一步创作：澄清、出方向、台词或分镜。没写时，选择方向后仍先写台词再分镜。只写了台词、没写分镜时，程序再请模型定一次下一步。第二次写成澄清或出方向就照做。只有第二次还是只有台词，才按原来的顺序把分镜接上，不把没排完的画面交给商家。排时间、综合审核和图片视频提交不接受模型指定，仍由程序在原位置执行。澄清和出方向仍是同一次入口调用。

新对话冻结本轮上下文，方案修订和上下文版本用于拒绝过期操作。澄清中的底部文字成为当前题答案，先保存在本地草稿，最终统一提交；图片检查中的文字成为修改意见，先进入策划，不能隐式触发视频。

第一阶段可返回 `reply`、`clarify`、`directions` 或沿已选方向继续 `plan`。`directions` 持久化独立 gate，`POST /api/projects/{id}/direction-select` 校验候选、修订、上下文并原子创建一次续写；选择不会提交图片或视频。澄清最多 4 题，问题数量由缺失信息决定；过滤后的问题必须保留实际回答方式。新候选先经独立 `direction_review`，全部通过后供用户选择。进入所选方案策划后，服务端校验商品依据和方向，联合起稿或内容稿交分镜协调后，程序生成实际镜头和完整台词时轴，再综合审核整条商品表达、动作状态与逐句声画。不新增用户确认门。左侧用已保存的商品受众/场景及所选方向的开场、中段、收尾组成创意摘要，不展示其他候选，也不重新调用模型；“修改方案”聚焦底部输入框且保留草稿，用户发送后沿用 `turns` 提交新一轮策划。新方案的“修改台词”将修改意图送回统一输入框，提交后联动重排画面、旁白与时间；旧方案继续提供原逐镜文字编辑。

执行事件按顺序保存，SSE 用游标增量刷新；前端还有快照轮询用于恢复。历史记录展示的是执行步骤和结果，不是模型内部思维链。超过 120 字符的已完成策划公开回复在对话中显示简短提示，原文按任务 ID 放入同一折叠区的“本轮策划说明”，与执行记录分开展示且不计入事件数量。历史说明不使用后来编辑的当前方案重新推导。等待回答或检查图片的任务不占用运行 worker。重试任务按当前事件分段中最近一次真实开始执行事件计时，普通步骤不重置；终点仅取本次尝试内的完成或等待事件，排除失败后的等待间隔。没有开始事件的历史记录回退到既有started_at，数据库与原始事件不改写。

## 本地规则与商品依据

规则库目前有 6 条原创整理的机制：感官细节、生活情境、外观揭示、操作讲解、问题与解决、有依据的对比。第一阶段使用完整规则集，服务端检查实际方向的品类适用性及引用事实是否满足前提；后续内容与分镜阶段只接收所选方向；内容阶段保留全部已验证商品事实，允许为同一表达补充依据。该过程没有联网检索，也没有加载第三方技能的执行能力。

`ProductBrief` 区分事实、未知信息和假设。事实记录 ID、文本和来源：

- `merchant` 来源只登记商家输入。已答澄清只保留用户选中标签或自由答案，不把模型问题正文、跳过占位或引用文件名前缀当作商家事实。
- 商家事实文本须为指定来源的连续原文摘录；句内限定检查保守拦截省略否定、不确定表达的摘录。
- `image` 来源必须属于本轮真实商品原图集合。此处验证的是引用关系，图片观察的语义准确性仍需要审查。
- 未知信息与假设不能替代事实引用。带功能或对比前提的规则，只检查该方向实际引用的商家事实，不借用其他方向或未引用条目。

服务端从本地规则写入规则 ID、版本与来源，第二阶段模型不能替换这些记录或商品事实。方向 ID、规则 ID、引用和明显重复内容受到结构检查；这些检查不证明创意在语义上足够不同，更不证明广告有效。模型仍可能误解商品、商家否定、场景意图或规则用法。

新 `Plan.strategy` 保存本轮记录。该字段可缺省或为 `null`，旧方案继续按原路径读取、编辑与生成；读取历史策略也不要求其规则仍在当前目录。编辑台词会深拷贝计划，保留策略和镜头引用。

## 当前文字模型的传输适配

`planner_transport.py` 对土豆 `gpt-6-sol` 的 `plan_review` 与 `plan_refinement` 使用 `reasoning_effort=medium`，storyboard 原有 high 档可由 `PLANNER_STORYBOARD_EFFORT` 选择 low/medium/high（缺省 high）。旧无阶段 Skill 的分镜仍保留原 low 档，其他模型与预算不变。实际HTTP参数与PlanningSession签名使用同一stage参数，旧high审核/返修不能直接当新medium结果重放，未变更阶段仍按原签名复用。该适配来自同稿诊断与返修请求的实际HTTP504，不能证明整体质量或速度提升。

仅该供应商/模型的请求设置read600/connect15/write60/pool15秒，并由兼容Python3.10的 `asyncio.wait_for` 限定单次总时长660秒；其他请求保留原等待行为。超时和外部取消都会关闭客户端，外部取消继续向上传递。high复验即使延长本地上限仍约301秒未返回，远端原因未确定；等待调整不等于故障根治，也没有增加现有临时重试数。

可选的文字加速不改变上述默认值。`PLANNER_STAGE_ROUTES` 按阶段指定 `provider:model[:effort]`；未列出的阶段，包括默认的 strategy，仍用主策划模型。只有同时配置 `PLANNER_FALLBACK_PROVIDER`、`PLANNER_FALLBACK_MODEL` 和 `PLANNER_FALLBACK_ON=timeout` 和/或 `504` 时，超时、HTTP 504，以及连接被掐断、读重置或 HTTP 502/520–524，才改用该文本模型。同一步对这种掐断最多再向原模型发一次；若上一次也在大约 100 秒断开，就不再发。一步的总等待不超过 `PLANNER_REQUEST_DEADLINE_SECONDS`。本进程记住会掐掉长非流式请求的供应商和模型。不会循环，也不作用于图片或视频提交。检查点里签名对不上的步骤连同其后的记录一起丢掉，从该步重算，前面匹配的步骤保留。最后一张恢复卡会按已保存的需求和已选方向重新排队。缺少对应密钥时跳过回退并只记录原因。`PLANNER_STREAM=auto` 先尝试 SSE。对方在首个文本前返回 HTTP 400、正文不是事件流、流在没有 `finish_reason=stop` 且没有 `[DONE]` 时结束、连接中途断开，或流式 `finish_reason=length` 时，若本次等待还够再发一次，同一模型改发非流式请求。该供应商在本进程内随后不再走流式，日志记 `stream_fallback`。剩余时间不够时改走已配置的超时回退。这两次恢复在指标里分别记 `nonstream` 和 `fallback`。最终仍无完整正文时，界面说明这一步没有在系统这边完成、需求已保留，并留一个「继续处理」作为最后入口。缺省 `off`。策略结果先在本地丢弃无效短概念、矫正钩子并接受有效的三个方向，记 `strategy_salvage`。方向审核若已写 `ready: true`，省略的机制、钩子、品牌世界、观众处境和一句话从审前方向抄回；仍不可用则退回审前方向，只保留仍然有效的文字修正，记 `direction_review_salvage`。失败诊断使用该阶段实际调用的模型，并附上校验原因代码。任务进度已经允许「继续处理」时，检查点最后一步即使已被标成完成，也会丢掉后重新排队。仍不可用时，在原来的等待预算里自动再请求一次：剩余不少于 30 秒就同一模型修正（`strategy_retry`），更短但仍不少于 1 秒且配置了超时回退就改用回退模型。这次额外请求的等待不超过剩余预算，也不会再串联下一次回退。`PLANNER_REQUEST_DEADLINE_SECONDS` 把单次读超时和总等待压到该秒数（允许 30–600），缺省不设置，因此土豆 gpt-6-sol 仍是 600/660 秒。这些等待参数不进入检查点；阶段路由或显式回退策略会进入签名。签名变了就从这一步重算，不会把另一个模型的回复当成原请求重放。

`PLANNER_MAX_REFINEMENTS` 缺省 2，可设为 0 或 1。`PLANNER_REFINEMENT_FORMAT=sparse` 时，非重组返修只给出差异补丁 schema；缺省仍允许补丁或全文，因为当前请求使用 json_object，模型仍可能返回全文，服务端两种都能合并。估时守卫会把“画面和台词都没变、只把估时调低”的节拍恢复成原估时；其余真实修改保留，恢复后的稿仍要能编译并通过独立复审，不会把恢复后的数字当成审核通过。综合审核仍返回每个镜头和每句台词的判定：通过项可以不写重复说明，但通过镜头上的时长下限和画面执行判断不能省，否则会放过真实的时间错误。审核按策划会话的顺序执行，不并行拆开。`PLANNER_SPECULATE_RECOMMENDED=true` 时，用户还在选方向就会为推荐方向预跑文字方案；不提交图片或视频。选中该方向时按阶段签名复用，选其他方向或改口则丢弃。示例里的整组快速配置见 `.env.example`，需要重启后生效。

## 广告表达、时间编排与最终审核

正式 `Ads Video` Skill 承担领域方法，旧 `ad_expression` 及协议版本仅作历史兼容。已知商品特点如何关联受众选择，须落实到实际台词、画面和动作，不能靠 `purpose`、事实 ID 或作者自评认定成立。只有外观资料时可以表达有依据的审美选择，不能编造功能或真实体验。

第三阶段将分类展开方法放在共用参考 `shared/script-expression.md`，仅注入 `ad_script / storyboard / plan_refinement / plan_review`。产品展示用产品与视觉关系推进，剧情/场景通过商品参与的人物选择与变化推进，人物讲解由角色向观众解释或演示；这不是三个固定镜头模板。声音按已选约定补信息、解释选择、推进关系或完成必要教学、强调和反差，不把所有带动作动词的话机械判为无效，也不因类型名称自动切换声音身份。共用参考同请求加载并记录版本，不增加一次模型调用。

`ad_script` 使用脚本规划（已并入原台词方法），产出核心表达、受众收获、商品作用和有序内容段落。每段区分目的、信息、画面职责、完整台词与 `timing`；后者估计动作/辨认时间、语音能否并行及前后状态。初稿还可协调，不固定句数、镜头数或临时秒点。

`JOINT_PLANNING_ENABLED=true` 且采用当前方向选择/渐进策划时，直接以事实、所选方向、固定要求和声音约定起草，不请求前置 `ad_script`。Storyboard Direction、脚本规划主文件/台词示例及一次共用表达参考同请求工作；`authoring_mode=joint` 仅标记初稿，局部修订仍严格使用 `draft_storyboard` 和 `repair_scope`。这是尚未通过速度验收的试验路径：初次真实样例暴露容量超限、多轮返修及失败，本地与示例配置均关闭。关闭开关保留原三阶段，用户确认位置、原稿和媒体不变。

`CONTENT_DRAFT_ENABLED=true` 是另一条默认关闭的初稿试验，只在方向选择、渐进策划有效且 joint 关闭时生效。保留 `ad_script → storyboard → plan_review` 三次调用；第一步只生成 `ContentDraft.beats` 的实际话语、可见内容与事实引用，不伪造摘要、目的、时长或动作容量。传输及进度阶段仍为 `ad_script`。它不再单独加载 content-draft 附录，技能资源与脚本规划的 `ad_script` 相同。既有导演阶段首次填写完整 `AdScript`、动作状态、时间需求和镜头，后续编译、固定要求、容量及综合审核全部保留。有效开关进入会话身份，禁止两种草稿的检查点混用。

轻量路径的作者输入不再把已选方向前的 `brief.assumptions` 当作新要求；这只作用于带 `draft_format=content_only` 且存在已选 production 的模型输入。原始用户消息、带来源事实、unknowns、创意含义及制作约定保留，存档和完整检查点签名不删该字段。已选方向约束意义与必要信息，只有用户明确固定原句才锁文字。

新综合审核逐镜返回 `visual_execution`，以实际 `description` 或 `continuity.camera_move` 原文定位视图与摄影变化；`unclear/conflict` 降低镜头与总体结论，不能用目的说明填补拍法。新回包即使夹带历史绑定也必须填写，历史已绑定记录仍可缺省。通过项可省去重复 `note`，失败原因、全部判定、时长、镜头/台词覆盖、摄影及省略引文仍保留；没有用程序填入肯定意见。审核输出格式版本与 schema 进入请求签名，语义正确性仍须真实样例核对。


`storyboard` 返回 `DirectorDraft`，包含完整协调后的 `ad_script`、`visual_direction` 与有序 `shots`。每镜 `coverage` 以相邻 `beat_id` 和相对权重表达内容覆盖，一段可跨相邻多镜，一镜也可承载相邻多段。未被用户固定的台词、次要动作与估计可一起调整；商品事实、故事核心、固定台词、人物/声音和目标片长仍受保护。模型不输出 `segments`、镜头起止或 `speech_spans`。

`compile_director()` 在分镜回复后校验内容覆盖顺序、稳定引用与固定台词，再复用 `generation_groups()` 和 `expression_schedule()` 确定生成段、内容组及说话窗口。覆盖权重分配镜头实际时长；镜头不能跨请求或在内容顺序中反复跳回。程序派生 `Shot.beat_ids`、整句 `SpeechSpan` 与其真实覆盖镜头；新路径初始 anchor 使用整句文本和完整窗口，不再请求模型抄写临时时轴或逐短语切镜。合法语音前后留白不要求等于切镜边界。确定性派生只证明覆盖与引用合法，不能证明具体画面语义正确。

`plan_review` 独立检查这一份实际最终方案。`PlanReview.checks` 包含商品关联、受众关联、事实支持、声画互补、自然口语和叙事推进六项；`execution_check` 包含动作容量与状态接续；`alignment` 包含广告表达、全部实际旁白时段及全部镜头的 AV 检查，每镜必须给出动作时间和切镜必要性 `pacing`。静默镜头同样检查。审核输入不以目的、自述证据或摘要充当结论，必须核对实际台词、动作顺序、父子物体依附和消耗状态、人物开口及具体窗口。

程序将已验证时轴投影为逐段 `execution_windows`，包含每拍实际 `beat_start/end`。明确并行时，动作可用本拍与镜头的实际交集；作者的 `visual_seconds` 是需求估计，其 `visual_end` 不能当作并行动作硬截止。非并行动作仍只能占用对应视觉窗口，不能挪用后面的讲话时间。返修进度的动作缺口采用相同交集计算，不借相邻内容时间，也不修改负面审核结论。审核只给结论与定位，不在同次审核中改稿。任一必需项失败都不能整体通过；明确失败或数值超时只能向上降级为失败，不能补项或将失败升为通过。通过后的 `Plan.plan_review` 由服务端 `reviewed_plan_sha256` 绑定实际所审内容，模型不填写哈希；修改事实、内容、镜头或时轴后不能沿用旧审核。

失败最多使用两轮 `plan_refinement`，复用 Storyboard Direction 和相同草稿契约。服务端按失败项限定可改段落、镜头及必要相邻状态，保护未受影响内容；范围内可调整台词、动作、估计和合并/增删镜头。已知容量或生成分组冲突与内容修正合计最多两轮，首轮容量修正后仍有一次语义修正机会。输入包含全部可得反馈、实际轮次和上限。仅改自评说明、同类同位置失败完全未减少或两轮耗尽时停止。程序重新排时后再完整独立综合审核，保留已有方案与素材，不重跑方向，不自动生成媒体。

未分类型的方案仍用每秒 2.9 字符向下取整的工程上限，含标点与空白；20 秒最多 58 字符，单拍最多 29 字符。已确认的产品展示、剧情／场景、人物讲解改用各自配置，默认约每秒 3.0、3.8、4.8 字符。这不是语速标准或推荐密度。动作与语音可并行时预算取较长者，不可并行时相加；完整句不跨独立生成请求。实际音长、发音与信息密度仍待媒体验收。

`Plan.ad_script`、旧 `script_review`、旧 `alignment_review`、新 `plan_review` 与 `Segment.speech_spans` 兼容历史缺省。`speech_spans=None` 沿用旧逐镜台词，空列表代表新静默段。旧记录不会自动迁移或获得虚构综合审核。普通文字修改先经 strategy 路由，再走三核心阶段，联动更新内容、画面与时间；直接编辑旧镜头台词会清除失效的内容及审核绑定，保留商品事实和策略。

新内容稿使用直接输出，分镜、局部修正和综合审核使用 low 推理与充足输出额度；阶段参数由 `stage_request_options()` 管理。服务端只解析最终 `content`，记录阶段、耗时与数值 token，不保存或展示 `reasoning_content`。减少串行调用是实现变更，不是已经验证的提速或质量结论。全部审核仍只针对文字计划，不声称听过生成音频或观看成片。

## 同一说话人与局部出镜

`ProductionPlan.speech_mode` 保留 `voiceover / character_dialogue / none`。可选 `speech_delivery` 不改写历史：缺省或 `visible_only` 继续要求人物台词窗口覆盖的镜头包含指定角色，并由审核确认全时窗可见开口。显式 `on_and_off_screen` 只适用于 `character_dialogue`，允许同一已确认 `speaker_id` 在商品特写或嘴部不入画的局部镜头延续声音，不新增第二位旁白。方向选择后这项决定同角色、声线与商品约束一起冻结，分镜编译器无权替旧方案升级。

新声音延续的综合审核要求每个 `AVSpanCheck.shot_visibility` 按顺序恰好覆盖台词实际相交的全部镜头，分别记录 `visible_speaking / off_screen / unclear` 及具体依据。整句 `speaker_visibility` 必须与逐镜记录一致，可为 `mixed`，但这个汇总不能替代逐镜检查。可见开口记录还须绑定该镜头的同一角色；全片至少有一次在实际台词时窗内可见其开口，静默露脸不能充当依据。单镜内可见性变化却没有足够时点依据时不能笼统标可见。旧严格模式仍不接受 `mixed` 或 `off_screen` 通过。

只有完整、合法且覆盖全部实际台词/镜头的记录都明确为 `off_screen` 时，程序才将 `ad_expression_passed` 和整体结论向下传播为失败，交现有语义返修。缺表、未知身份或遗漏仍是无效审核，不猜测、不补可见证据；`unclear` 不能通过。审核格式恢复保留原有否决，不能把格式修正变成对未修改方案的放行。

`CharacterSpec.appearance` 为可选 `face_visible / partial_only`；新创作角色须明确填写，旧角色不回填。`partial_only` 仍是有身份的角色，镜头应引用其 ID，不能被摘要称为无人；它不能成为 `character_dialogue` 的唯一说话者。同一人的脸、手和附着头部的发丝不拆成多名角色。明确的独立发束或概念材质可以作为道具，程序不根据“发丝”一词替模型猜载体。角色仍沿用每人一张组合四视图，局部设定不改变当前图片确认和参考素材绑定流程。

视频编译器根据保存的声音与出镜约定要求同一人物持续说话，只有实际可见开口画面配合口型；纯商品画面不为对口型补人，局部角色不因参考图有脸而自行增加露脸。这些是制作提示与文字计划约束，尚不是原生视频声线、口型或人物一致性的实测结论。

## 计划、素材与最终媒体

计划按生成段组织，每段包含多个镜头和独立 `speech_spans`。镜头记录局部时间、可独立使用的完整画面描述、内容节拍与事实引用；旁白另行记录句子和短语窗口。`segment.prompt` 只提供场景参考图的统一视觉上下文，不参与新视频请求的自由文本拼接。视频提示由服务端依据 `shot.description`、实际旁白时段和短语对应编译，所以镜头描述必须保留场所、灯光、商品特征和状态衔接。旧方案继续使用原提示与镜头台词路径。界面展示累计时间，提交时保持段内时间；编译和结构检查不代表模型会严格遵守镜头或发音时码。

商品原图与生成场景作为共享参考进入视频请求，不要求先生成每个镜头的图片。新方案使用`continuity_v1`：10–30秒在一次请求内编排多个镜头；31–60秒由`generation_groups()`在完整内容节拍边界分组，单次2–30秒，优先场景转换。相邻节拍共享`continuity_group`或`boundary_before=continuous`时不得拆开；找不到可容纳的边界则要求重新策划，不暗改总时长。`Plan`再次核验实际段时长与节拍分组。旧方案缺省`legacy_10s`，继续每次请求10秒和短尾裁切；读取不会自动迁移。新方案原声随视频返回，合成时保留音轨、统一规格并设置峰值余量；旧画外音路径单独兼容系统 TTS 与原字幕。

导出清单保存生成策略、来源片段、实际导出规格和预期台词时间。`continuity_review`记录实际生成组数与请求接缝数，但声线与转场检查仍为`not_verified`；单次生成不是质量验收结论。`expected_speech_timeline` 是计划换算结果，不是语音识别或强制对齐结果；自动技术检查通过后仍标记需要人工复核。应用尚未把离线 ASR 分析接入自动内容验收。

素材和成片保留版本。内部重合成可以复用原素材而不新增供应商提交，当前没有公开重合成 API；画布通过当前成片的来源链找到实际使用的场景，新方案不能误用旧场景作为已完成结果。

## 第四阶段审核与返修交接

新鲜综合审核若使用 `supported_by_cut`，须附 `temporal_omission_evidence`：省略动作、当前镜头入口/出口边界及真实相邻画面原文。程序核对实际 cut/scene_change 和摘录来源；摄影机切换视角不构成商品完成转动的证据，动作语义由独立审核判断。`no_omission` 不增加必填，旧绑定审核不补造证据，方案指纹规则保持。

每次 `plan_refinement` 从当前候选重算容量；仅在当前稿确实对应最近一次编译结果时提供执行时窗。稿件变化后旧窗口失效，不能用旧预算继续修改。完整新稿仍执行同一次完整综合审核。

审核记录纠正耗尽、记录再次无效或补格式抹去原有否决时，返回 `planning_review_incomplete`；完整内容拒绝继续使用 `planning_content_failed`。总请求额度耗尽单独为 `planning_request_limit`。前端对审核未完成、无效回复和次数停止只提供“继续对话”聚焦输入框，后端不允许直接重提同一步骤；不自动发送消息或更改需求。原请求、检查点、失败历史和已保存成果保持。

HTTP故障诊断仅保存允许的阶段、耗时、合法状态码或异常类型。无HTTP状态不推断504，不记录授权头、供应商错误正文、异常全文或模型思考。该诊断不增加重试额度。

## 有界提交与恢复

- 一次未重试的新创意流程，选择前 strategy 与 direction_review 共 2 次，选择后内容稿、分镜协调与综合审核共 3 次，通常合计 5 次文本请求。普通文字修改包含 strategy 路由，通常 4 次。最多两次局部修正，每次成功排时后独立全审；已知容量错误共享两轮上限，同问题无改善提前停止。空回复仅在原步骤有整轮一次恢复额度。主动重试、新对话和媒体另计，不无限修复或自动开始制作。
- 各模型阶段之间及保存结果前校验取消和版本状态。已经发出的模型请求可能仍计费，取消用于阻止后续调用与晚到结果覆盖。
- 一次制作按方案提交一张场景图及每角色一张组合四视图；视频上限取配置上限与当前方案实际生成段数的较小值。
- 图片请求发出前保存磁盘回执，视频请求发出前保存数据库记录。得到远程任务 ID 后，恢复优先继续查询、下载和合成。
- 未能确定远程服务是否受理时进入 `submitted_unknown`，不自动重复 POST。调用次数上限不等同于金额封顶。
- 同版本重复生成请求复用已有任务；重启和恢复不会清零已记录的提交次数。新版本的再次制作可能产生新的费用。
- 取消停止后续本地工作，不能保证撤销已被远程受理的任务或退还费用。
- 只有必需媒体齐全并通过技术检查，才登记当前成片；失败片段和旧版本不能冒充新成片完成。

SQLite 任务记录和租约承担持久执行状态。`fcntl` 文件锁防止两个服务同时恢复同一数据目录；当前不是多进程队列或分布式调度系统。

## 策划进度接续与作品状态

`planning_session.py` 在任务私有 `payload.planning_checkpoint` 中保存按顺序绑定输入哈希的模型阶段结果、请求次数及重试额度。发出请求前先持久化次数，返回后保存结果；worker重启重放已完成结果，仅继续未完成步骤。哈希包含实际输入、模型、阶段参数、Skill与素材实际字节；规则或输入变化会停止沿用，不能让旧审核匹配新内容。检查点不进入公开API，回放不重复登记已完成阶段的Skill事件。

临时连接异常、HTTP 408/429/5xx整轮最多自动重试两次，成功但正文为空另有一次机会。默认整轮最多12次文本请求；语义修正最多两轮，计数随阶段回放保留。用户明确重新尝试只为未完成请求增加有限额度，保留已完成结果；该入口事务内核对项目、修订、需求版本、当前状态和检查点，重复点击不能覆盖运行中进度。结构、内容和凭证问题不进入传输重试。已受理媒体任务的GET查询可有限重试，图片/视频POST及未知受理保护不变。

项目返回派生的 `result_status`、`result_revision` 与 `work_status`：成果仅由当前指针关联的本项目ready成片确定，工作状态沿用原调度状态。新方案与新对话不替换成片指针；只有成功发布才切换。历史failed项目无需改写数据即可显示已有成果。前端在对话与画布保留播放/下载，分别显示本次修改状态；请求失败、内容失败、连接配置、受理未知与失败视频段使用不同入口，不显示通用“恢复任务”。

## 本地接口与数据边界

主要接口包括项目/上传、`turns` 对话、计划编辑、`generate` 准备图片、`creative-confirm` 图片确认、`retry`、`cancel` 和事件流。内部`continuity`入口只把已完成、已确认的10–30秒历史原声方案升级为单次生成：事务内校验当前版本、来源回执和图片哈希，保存新修订及幂等任务，复用确认图片。它不重写文案或绝对音画时间，不修改旧成片；当前没有新增面向商家的按钮。修改请求携带版本信息，避免过期页面覆盖新版。

预览通过 `/media/{asset_id}` 读取已登记媒体；下载使用 `?download=true` 触发附件响应，媒体支持 GET、HEAD 和 Range。前端接收素材 ID 与本地访问地址，不接收服务端路径、密钥或完整供应商响应。

连接可由 `.env` 或本机 `/setup` 提供。图片、文本和视频任务会发给所配置服务；应用不是完全离线生成工具。服务绑定 loopback，并有来源检查，但没有账号、用户授权或多租户边界，不能直接改绑定地址作为公网部署方案。

数据库与媒体共同组成项目数据。备份、迁移需保留两者及引用关系；路径变化后应重定位已有记录。`data/`、`.local/`、`.env` 不进入公开仓库。

## 后续边界

第一、二阶段由用户暂时接受，第三阶段分类脚本、分镜与声音协同已进入实施验证并等待用户验收。工程通过与三类真实文本的内容通过分开记录，不将测试替身的通过结论当成真实质量接受率；当前记录见 [STAGE3_ACCEPTANCE.md](STAGE3_ACCEPTANCE.md) 与 [VALIDATION.md](VALIDATION.md)。

当前已接入本地规则、内容稿、分镜协调与独立综合审核。P2 轻量外部参考检索、P3 实际生成图片语义回检、P4 真实音视频检查，以及基于成片质量问题的定向修复闭环仍未完成。对话改稿会重排计划，供应商失败重试不能替代成功成片的质量修复；不能承诺只改某个成片物体或局部像素不变。没有成片质量或营销效果改善的验收结论。

## 历史四阶段兼容

普通产品使用新的三核心阶段；未提供 `progressive_planning_enabled` 字段的旧自定义适配器保留选择后的 `ad_script → script_review → storyboard → alignment_review` 四阶段协议。旧 `ScriptReview` 记录仍可读。这些旧资源阶段不再单独注册：写稿试验和旁白初稿改加载脚本规划的 `ad_script` 资源，旧分镜改加载当前分镜资源，旧脚本审核和旧对齐审核改加载方案审核资源。这不是把参考检索或成片质检接进默认流程。

旧路径的 `storyboard_repair` 仍只处理原合同允许的时间或引用问题，并保留其原有次数、固定内容及取消/版本保护。新路径的最终时间由程序派生，不叠加这次旧修复请求；新路径的容量与局部内容修正合计最多两次 `plan_refinement`，无改善可提前停止。传输错误、解析错误、未知事实、非法引用或缺项不能伪装成可以自动修好的审核失败。

## 模型上下文与检查点身份

`planner_model_context()` 仅在实际发送边界精简已知 Skill 追溯字段、Schema 的 title 注解和可完全重建的重复台词/整句 anchor；业务 title、事实、固定台词、动作状态、说话人与细粒度 anchor 保留。程序追溯和请求签名仍用完整 `planner_wire_context()`，并签入投影版本；实际推理参数同样入签名。联合路由写入本轮身份，跨路由或参数变更不得伪装成原请求回放。已保存方案和成片直接读取，不重跑策划或覆盖；规则不同的旧未完成检查点须新一轮需求，不能自动移植旧结果。

## 文字规划返修与审核输出（2026-10-03）

局部 `plan_refinement` 可返回受限 `patch` 或原完整可编辑稿。patch 只能修改本轮范围内的既有内容/镜头 ID，嵌套 timing/continuity 逐字段合并，未列内容从当前候选原样保留；未知、重复、越权和 null 被拒绝。合成后的完整候选继续对最初 before 执行原范围、固定台词及估时守卫，并重新排时与独立综合审核。即使本轮允许全局容量重组，也可选择只修改原有身份的更窄patch；真正需要增删、合并或重排段落/镜头时，使用原完整分支。当前候选身份与原范围不兼容时不能构造稀疏合同，改走原完整分支，不扩展权限。返修输出版本仅进入该次请求签名。

综合审核的通过项允许省略重复 note；结论、覆盖、逐镜动作估计、摄影实现引文及必要省略/说话人依据仍必须完整。摄影实现按实际内容联合判断，不按术语字形判矛盾。新审核另外以可重建且匹配最终方案的实际排时，计算每镜合法动作窗口的并集；不能借用非并行段的语音窗口。这个并集仍用于容量缺口。模型自己估计的动作需求超过镜头实际时长时，程序降为失败，并可附明确标记的数学依据，不再为补该依据请求一次格式修复。镜头本身够长时，不再用更短的相交窗口把通过改成失败。能放进镜头并不证明动作语义可行。历史排时无法可靠重建时不猜测，旧绑定审核保持可读，fresh 调用不能冒用旧绑定豁免。
