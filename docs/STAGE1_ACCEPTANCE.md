# 第一阶段验收：需求、商品依据与广告倾向

日期：2026-10-02。本文定义验收合同与人工基线，实际执行结果应另附记录。用户已要求每个阶段验收通过后再进入下一阶段；本阶段不能用后续阶段的计划替代已完成工作，也不能自动继续第二阶段。

当前主流程是内容稿 → 分镜落地 → 综合审核。本阶段补充入口与事实基础，不重新引入多轮完整策划，也不宣称三类脚本生成、语义审核、人物口型或成片质量已经完成。历史广告表达评估文档中的旧流程描述不能作为当前实现依据。

## 广告倾向的名称与含义

三个选项表示广告的**主要表达方式**，可以混合使用。电影感、科技感、生活化属于风格；投放渠道和声音安排也应分别理解，不能与主要表达方式混为一项。

| 当前名称 | 主要表达方式 | 兼容内部值 |
| --- | --- | --- |
| 产品展示广告 | 以产品为主角，展示外观、功能或使用效果；不限定大片感，也不以产品特写自动证明性能 | `brand_tvc` |
| 剧情／场景广告 | 通过人物处境、行动与产品参与后的变化展开；不要求完整小短剧或反转 | `scene_story` |
| 人物讲解广告（口播） | 人物面向观众讲解、演示或分享产品；可以只讲透一个购买理由，不要求罗列多个卖点 | `presenter_pitch` |

`brand_tvc` 仅为兼容既有项目和接口而保留的内部值；当前显示含义是“产品展示广告”，不能继续把 TVC 当成与剧情、口播互斥的行业分类。旧卡片与历史回答保留当时的名称；当前已保存倾向显示新名称，不因此重写历史内容。`auto` 仍表示“根据商品推荐”，不是已经完成某种类型推荐。

## 本阶段完成条件

1. **广告倾向可选、可存、可改。** `project.ad_form` 与 `brief.ad_form` 使用 `null`、`auto`、`brand_tvc`、`scene_story`、`presenter_pitch`。未选择为 `null`；用户明确授权推荐或跳过该题为 `auto`。`ad_form` 澄清卡沿用统一输入，不增加另一张填写表或额外确认弹窗。卡片提交、自然语言选择、刷新重进、局部改稿及明确改选应保存一致。
2. **正确理解选择的语气与范围。** 否定某类不代表选择另一类；条件讨论和询问区别不代表改选；旁白属于声音安排，不等于人物讲解广告。旧类型被明确否定后不能继续当作当前有效选择。明确提出改选但主要方式混合或尚未确定时，保留约束并回到固定选择卡，不凭关键词决定。只改某句台词、旁白或某个镜头时，不改整条广告的倾向。本文不要求用确定性字符串规则穷举自然语言。
3. **商品事实、创作设定与缺口分开。** 已知事实和用户限制进入现有事实模型，不重复创建同义字段；事实有依据且来源范围正确。创意愿望、外观猜测、合成资料、未来希望验证的功能不能升级成商家确认事实。更正事实后不能同时保留矛盾的有效事实。事实不足可提出受依据限制的方向，不要求用户填完所有参数。
4. **入口不重复追问，也不因只有图片失败。** 已有类型、时长、商品资料先提取；无文字的图片输入保留素材关联，再问必要缺口。本基线预置的图片观察只用于逻辑测试，不证明图片识别正确。
5. **提供可复用基线和实际工程证据。** 下述夹具结构可读，入口关键场景通过相应 API、状态或界面检查，记录实际输入和持久化结果。例稿只是参考候选，人工查看后可修订。离线替身返回正确字段不能代替真实模型理解验收；未测项要写“未测”，不能自动算通过。

交付时分别报告工程通过、人工已核对、未验证三项。若仍存在阻断本阶段核心操作的问题，继续修第一阶段，不进入第二阶段。真实模型或媒体调用只能在对应授权和隔离环境内开展；本基线没有执行这些调用。

## 基线文件与来源边界

| 文件 | 内容 | 可以证明什么 |
| --- | --- | --- |
| `tests/fixtures/intake_acceptance/reference_samples.json` | 三种商品 × 三种广告倾向，共 9 份短完整参考稿；每份含事实、假设、缺口、主旨、20 秒分镜、声音原句、状态连续性 | 提供人工讨论的具体候选；不代表模型已能稳定生成 |
| `tests/fixtures/intake_acceptance/intake_cases.json` | 19 个入口用例，含选择、跳过、保存、修改、否定、假设、仅图片与事实更正 | 定义可观察的期望；夹具本身不是执行记录 |
| `tests/fixtures/intake_acceptance/regressions.json` | 8 个历史、构造反例或正向边界 | 防止混淆原始观察与新编案例，保留有依据的人工判断 |
| `tests/test_intake_baseline.py` | 纯标准库的文件、引用、覆盖与计划时间完整性检查 | 仅证明夹具结构完整，不判断广告语义与真实音长 |

所有新商品参数均为**合成测试输入**，不属于实际商家，不能写回用户项目。只有 `regressions.json` 明确标为 `historical_actual_excerpt` 的短句来自既有观察。蛋糕“吃完又取樱桃”以用户报告为依据，新写最小反例，未冒充原始分镜逐字记录。没有复制项目标识、数据库路径、原图、供应商回执或密钥。

参考稿按商品分别共享同一事实集，避免以“另一种广告类型可以多编参数”制造差异。黑巧 70% 仅修饰所用黑巧原料；挂钩、杯子、薄册等道具不等于附送配件；人物属于创作角色，不代表真实用户体验。每句声音都写明作用，避免通过“每镜必须有旁白”强行填句。

三份口播样稿只有同一讲解者，在说话镜头中保留嘴部可见，适应目前单说话人边界。它们没有验证实际口型，也不要求第一阶段开放未经验证的数字人成片能力。三个广告倾向与声音模式不作一对一绑定；这里的参考选择不是全局路由规则。

阅读架是本组**留出商品**，避开运行时已有花瓶、折叠购物袋示例。不注入运行时提示，不用它调整当前规则。由于参考稿可被开发者阅读，它不是保密盲测集；后续评测还需保留未参与调参的新输入。只要根据某个留出样本修改规则，就应把该样本转为回归集，不能继续称作独立泛化验证。

## 人工阅读参考稿的方法

先只读同商品的输入，再依次读三种类型的最终画面与原句，填写以下结果。不能仅凭 `core_message`、`speech_role`、事实 ID、审核的“通过”字样或关键词命中作结论。

| 维度 | 需要定位的证据 |
| --- | --- |
| 商品依据 | 哪句或哪个画面主张被哪个输入事实支持；有无扩大原料比例、性能或适用范围 |
| 消费者理由 | 商品特点与当下选择有什么具体关系；是否只是常用、好看等泛用形容 |
| 类型差异 | 产品展示的视觉组织、剧情／场景的因果、人物讲解的直接解释是否在成稿中成立 |
| 声画分工 | 删去这句会丢失什么；必要操作说明可以成立，重复动作或空口号不能靠字数通过 |
| 物体与动作状态 | 每镜开始和结束时商品在哪里、是否完整、谁拿着什么；动作是否有前提 |
| 自然表达与时间 | 实际朗读是否完整，有无过密或碎句；计划秒数不能代替合成音长 |

每项填 `pass / fail / unknown / not_applicable`，并引用具体样稿、镜头和原句。关键项 `unknown` 不算通过；分歧保留双方理由，不用另一轮同模型自审自动裁定。人工审核结果另存执行记录，保留原始候选与修订稿，避免只展示挑选后的好结果。

九份样稿是后续共用的质量标尺，**本阶段不要求运行时已达成第二、三阶段所有内容效果**。但发现样稿有错误应先改样稿，否则不能作为标尺。

## 可重复执行的入口检查

1. 使用隔离项目与替身供应商，不读取生产数据库或真实密钥。清晰区分自然语言理解模型替身、真实解析逻辑、存储层和界面层的验证范围。
2. 从 `intake_cases.json` 选择相应场景，保留其 `initial_ad_form` 和所有用户轮次，不只把最后一句提交给测试。
3. 核对答复、澄清卡、项目持久化值、下游 brief，必要时刷新并重新读取。逐项记录 `expected_behavior` 与 `must_not`，不可仅断言 HTTP 200。
4. 使用事实缺口场景核对“没有证据”的数据去向。仅图片案例不能继承同类商品其他夹具中的商家参数。
5. 记录结果与未覆盖路径，完成本阶段评审。未运行的人工案例保持 `not_run`；不能因夹具完整性测试通过而批量置为通过。

### 本次验收问题的必测回归

以下步骤来自实际用户操作，应用于隔离项目复现。复用真实用户原句，不等于运行了真实模型；真实模型未调用时必须记为“未测”。原用户项目只作经授权的诊断依据，不作为可被测试重置的数据。

| 场景 | 逐项验收要求 |
| --- | --- |
| 原操作完整链：旧卡选择“TVC 广告大片” → “我想换个剧情广告” → “我想改广告倾向，想做口播广告” | 每轮分别应为 `brand_tvc` → `scene_story` → `presenter_pitch`。核对项目保存值、当前任务冻结的上下文、下游 `brief.ad_form`、刷新后摘要；不能只验证最后一轮或只看模型答复。旧卡选项按兼容 ID 识别，当前摘要按新名称显示。 |
| 明确改选但主要方式未确定，或同时要求多种方式而没有主次 | 返回同一套固定广告倾向选择卡，让用户确定主要方式或选择推荐；不重复新建输入框，不沿用旧候选冒充新倾向已完成，不将未确定状态静默选成某一类。 |
| 局部修改：“把第二个镜头的台词改成……”或“这里改用旁白” | 当前广告倾向不变；局部声音与文本修改不升级为整条路线切换。 |
| 模型答复与保存冲突 | 模型不能仅口头说“已切换”或“按口播继续”，同时系统仍保留旧类型。以实际保存状态决定可确认的内容；未确定的改选回选择卡，不用模型的肯定语气替代持久化。 |
| 已有方案、图片或视频时改选 | 老方案及媒体仍可查看、播放、下载；未产生并接受新版本前，不覆盖已有方案，不把旧媒体标成新倾向生成结果，不自动重复提交图片或视频任务。 |

这组回归验证入口选择及传递的一致性。三个创意是否真正符合所选类型、是否让观众看见商品卖点，属于第二阶段；脚本、分镜和声音是否形成相应表达，属于第三阶段。即使本表工程检查全过，也不能把这些内容效果或本次用户验收自动标为通过。

夹具完整性自检命令（不导入应用，不读配置，不发网络请求）：

```sh
python3 -m unittest discover -s tests -p 'test_intake_baseline.py' -v
```

这六个检查只保护验收材料的引用关系、三类覆盖及来源边界。业务实现的回归测试另行执行。

## 后续阶段共享的质量与耗时口径

| 指标 | 定义与记录要求 |
| --- | --- |
| 首次可用率 | 第一份未经语义返修的完整方案经人工关键项验收通过的用例数 / 所有正式开始的用例数。技术失败、内容失败均在分母内；外部主动取消单列。不能把成功样本作为分母。 |
| 有界返修后可用率 | 在约定预算内最终通过的用例数 / 同一批全部开始用例数。与首次可用率分开，不用修后结果回填首次结果。 |
| 成功全耗时 | 从用户提交完成该次必要输入，到第一份人工可接受候选就绪；包含排队、模型请求、校验及自动返修等待，人工事后判读耗时不混入。记录每例与样本量，可报中位数和分位数；小样本不推断总体稳定性。 |
| 失败耗时 | 同一起点到明确失败或预算停止；不得只报告成功用例的快耗时。超时上限、用户取消和不可确定的供应商受理状态分别记录。 |
| 返修次数 | 内容稿重写、分镜局部修复、审核格式修复、网络重试分别计数；同一次内容修复造成的多请求不能伪装成一个便宜调用。 |
| 请求与费用 | 各阶段实际请求数、供应商收费状态和已知费用单列；未知费用保持未知，不从耗时猜测。 |

文本阶段的一次完整用例从“需求已经具备且用户选定方向”开始计时。入口澄清阶段另记录本轮用户提交到澄清或方向候选可见的耗时，**两种起点不要混算**。用户停留选方向的时间单列，避免把人思考时间算成模型耗时，也避免把系统等待排除。

每条人工记录至少包含：`case_id`、代码与规则版本、输入快照、是否真实模型、候选及修订引用、开始/结束时间、各类请求和返修数、逐项判定及原句证据、最终状态、未验证项。有限样本上的通过率不等于线上任务成功率或广告转化率。
